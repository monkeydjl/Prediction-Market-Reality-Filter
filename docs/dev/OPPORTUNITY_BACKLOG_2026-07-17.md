## 0. 如何使用本文档

| 符号 | 含义 |
|------|------|
| **P0** | 安全 / 闭环能否转起来；不做则其它优化难验证 |
| **P1** | 精度或产品主路径，投入产出比高 |
| **P2** | 明显增强，可排期 |
| **P3** | 体验 / 平台化 / 长尾，不阻塞主路径 |
| **BY-DESIGN** | 有意取舍，改前需产品决策 |

**推荐原则（与哲学一致）：** 先让闭环转起来并积累 resolved 样本，再加深引擎与因子——「反馈优于空泛智能」。

**硬约束（Sports Kernel）：**

- `prediction_kernel.py` / `domain.py` / `learning_service.py` / 已有 `engines/*.py` 在既有 Phase 中约定「零侵入」扩展时优先走 Protocol + FactorRegistry + 新引擎注册。  
- 新表用 `kernel_` 前缀；feature flag 默认 OFF。  
- 不做自动下注 / 仓位 / 资金管理。

### 1.4 引擎与因子现状（关键结论）

| 路径 | 引擎 | 实际消费的因子 | 备注 |

1. `GET /api/health` 为 ok / 明确 degraded 原因  
2. 手动或调度完成一轮 `discover`，`event_store` 有新记录  
3. 存在 `freeze_prediction` 与后续 resolve 打分  
4. Kernel 路径：对一场已知 `match_id` `POST` 预测成功  
5. （可选）市场链接 → edge → settlement 有一条完整样例  

**验收失败时不要先做复杂引擎调参**——先修数据源 / flag / 鉴权 / 调度。

同一条——`TeamFeatures` 合同与它的类型同步 CI 都不动。**这两个比率在整个仓库只有一个写者**（`_shared.py:666`，测试用 glob 断言这份清单精确等于单元素），`world_cup_adapter._build_custom` 根本不调 `enrich_situational_features`，所以「两个组合根」那个坑在这个字段上是关着的。**h2h `_adjust_home_edge` 函数体内的字面量，这正是 h2h 一点下限都没有的原因——它是唯一不路过那个函数的投票者；现在提成 `_VOTE_FLOORS` + `_floored_3way`，两条路径都读同一张表，测试把表抬到 0.30 后断言**两条**路径的最小腿都跟着变（否则一方仍在抄自己的字面量也能通过）。**但只加下限不够**：100% 主胜的记录仍投 `H=0.943`，比任何同胞能达到的都极端（最宽的同胞 elo 是 `H=0.590`）。**所以改成按样本量收缩，而不是硬钳**：`w = n / (n + k)`、`k = _H2H_PRIOR_MATCHES = 2.0`——可以一句话说清：**一个完整赛季的交锋恰好值一个先验**；100% 主胜在 n=2 投 0.700、n=20 投 0.924。选斜坡不选钳位是量出来的：国家队语料（`world_cup_historical_results`，49,465 行 / 336 个队键 / 7,535 组对阵）里 n=1 占 26.6%、n≤2 占 43.6%、n≤3 占 52.8%，而 **n≥8 占 23.8%、n≥20 占 6.8%**，`aggregate_h2h_meetings` 本身就按
