## 1. 审查流程总览

```
开发者          审查者           自动化           合并
  │               │               │               │
  ├─ 创建PR ──────┤               │               │
  │               │               │               │
  │               ├─ CI/CD 通过? ──┤               │
  │               │   ├─ 类型检查   │               │
  │               │   ├─ 单元测试   │               │
  │               │   └─ Lint      │               │
  │               │               │               │
  │               ├─ 人工审查 ──────┤               │
  │               │   ├─ P0 阻断? ──→ 开发者修复   │
  │               │   ├─ P1 建议? ──→ Issue 跟踪   │
  │               │   └─ P2 优化? ──→ 可选改进     │
  │               │               │               │
  ├─ 修复/回应 ───┤               │               │
  │               │               │               │
  │               ├─ 批准 ────────→ 合并 ─────────┤
  │               │               │               │
```

### 核心原则

1. **CI 先行**: 自动化检查不通过，不进入人工审查
2. **分级处理**: P0 阻断合并，P1 跟踪修复，P2 不阻塞
3. **时效承诺**: 审查不超过 1 个工作日
4. **可追溯**: 每条 P0/P1 意见对应一个 GitHub Issue

## 2. 角色与职责

| 角色 | 职责 | 权限 |
|------|------|------|
| **开发者 (Author)** | 编写代码、自检、创建 PR、回应审查意见 | 创建 PR、修改代码 |
| **审查者 (Reviewer)** | 按标准审查、分级标注、批准/拒绝 | Approve / Request Changes |
| **维护者 (Maintainer)** | 最终合并决策、标准维护、争议仲裁 | Merge、Close PR |
| **CI/CD 系统** | 自动化检查 (类型、测试、Lint) | 阻断不通过的 PR |

### 审查者要求

- **后端 PR**: 至少 1 名熟悉 Python/FastAPI/数据持久化的审查者
- **前端 PR**: 至少 1 名熟悉 React/Next.js/TypeScript 的审查者
- **全栈/管道 PR**: 至少 2 名审查者 (后端 + 前端 或 后端 + 架构)
- **涉及数据持久化变更**: 必须有熟悉双层存储 (JSON+SQLite) 的审查者

### 审查分工矩阵

| 变更范围 | 后端审查者 | 前端审查者 | 架构审查者 |
|----------|-----------|-----------|-----------|
| `backend/services/` | ✅ 必须 | — | 建议 |
| `backend/app/memory/` | ✅ 必须 | — | ✅ 必须 |
| `backend/app/models/` | ✅ 必须 | — | 建议 |
| `frontend/src/` | — | ✅ 必须 | — |
| `frontend/src/lib/api.ts` | 建议 | ✅ 必须 | — |
| 管道编排 | ✅ 必须 | — | ✅ 必须 |
| 配置/部署 | ✅ 必须 | 建议 | — |
| 文档 | — | — | — |

## 3. PR 生命周期

### 3.1 阶段一: 开发者自检 (Pre-PR)

在创建 PR 前，开发者必须完成:

```
□ 本地运行并通过所有测试: python -m unittest discover -s tests
□ 本地运行并通过 Lint (如有配置)
□ 审查自己的 diff，确认无调试代码/注释残留
□ 确认 .env 未包含在 PR 中
□ 确认无硬编码密钥
□ 填写 PR 模板 (见 .github/PULL_REQUEST_TEMPLATE.md)
□ 为复杂变更附上设计说明或架构图
```

### 3.2 阶段二: CI/CD 自动化检查

PR 创建后自动触发:

| 检查项 | 工具 | 通过标准 | 不通过处理 |
|--------|------|----------|-----------|
| Python 类型检查 | `mypy` (逐步引入) | 0 errors | 修复后重推 |
| Python Lint | `ruff` 或 `flake8` | 0 errors | 修复后重推 |
| 单元测试 | `python -m unittest` | 全部通过 | 修复后重推 |
| 前端构建 | `npm run build` | 成功 | 修复后重推 |
| 前端 Lint | `eslint` | 0 errors | 修复后重推 |
| 敏感信息扫描 | `detect-secrets` 或 `ggshield` | 0 findings | 🔴 立即阻断，检查密钥泄漏 |

**注意**: CI 的具体工具配置可根据团队情况逐步引入。当前最低要求: 单元测试 + 构建通过。

### 3.3 阶段三: 人工审查

#### 审查启动条件
- CI 全部通过 (或未通过的项已确认与本次变更无关)
- PR 描述完整，包含变更原因和影响范围

#### 审查时限

| PR 规模 | 目标审查时间 |
|---------|-------------|
| 小型 (<100行) | 4 小时内 |
| 中型 (100-500行) | 1 个工作日内 |
| 大型 (>500行) | 2 个工作日内 |
| 紧急修复 | 2 小时内 |

#### 审查输出

每条审查意见格式:

```
🔴 P0 | 🟡 P1 | 💭 P2 · [类别代码] · 简短标题

位置: 文件路径:行号

原因: 解释为什么这是问题

建议:
- 具体的修复方案
- 替代方案 (如有)
```

### 3.4 阶段四: 开发者回应

| 意见级别 | 开发者响应要求 |
|----------|---------------|
| 🔴 P0 | **必须修复** 或 说明不修复的充分理由 |
| 🟡 P1 | 修复 或 创建 Issue 跟踪并链接到 PR |
| 💭 P2 | 自行决定; 采纳或礼貌回应 |

**沟通协议**:
- 每条审查意见单独回复
- 如不同意，解释原因而非简单拒绝
- 修改后标记为 resolved

### 3.5 阶段五: 批准与合并

#### 批准条件

```
□ 所有 P0 问题已解决
□ 所有 P1 问题已修复或有跟踪 Issue
□ 所有审查者的 Comments 已回应
□ 审查者已点击 "Approve"
□ CI 仍然通过 (或已确认无关)
```

#### 合并策略

| 分支类型 | 合并方式 | 说明 |
|----------|----------|------|
| `feature/*` → `main` | Squash & Merge | 保持 main 历史简洁 |
| `fix/*` → `main` | Squash & Merge | 同 feature |
| `main` → `release/*` | Merge Commit | 保留合并点 |
| 紧急热修复 | Merge Commit 或 Squash | 视紧急程度 |

#### 合并后

```
□ 删除源分支 (GitHub 自动)
□ 关闭关联 Issue (如 PR 描述中有 "Closes #N")
□ 通知相关方 (如涉及 API 变更)
```

## 4. 审查执行指南

### 4.1 审查者工作流 (60分钟审查节奏)

```
[5min]  整体浏览 PR 描述和变更概览
       ↓
[15min] 逐文件审查，标注问题
       重点: 数据持久化变更、管道变更、API 变更
       ↓
[10min] 检查跨文件一致性
       - 新增代码是否与现有模式一致？
       - 类型定义前后端是否对齐？
       - 管道输入输出契约是否匹配？
       ↓
[10min] 运行本地验证 (可选但推荐)
       - 拉取 PR 分支
       - 运行相关测试
       - 对管道变更做冒烟测试
       ↓
[10min] 编写总结性评论
       ↓
[10min] 提交审查结果
```

### 4.2 审查优先级矩阵

不是所有代码都需要同等深度的审查。按照风险分级投入精力:

| 代码区域 | 风险等级 | 审查深度 | 说明 |
|----------|----------|----------|------|
| `event_store.py` + `prediction_store.py` 联动 | 🔴 极高 | 逐行审查 | 数据完整性生命线 |
| `calibration_feedback_service.py` | 🔴 高 | 逐逻辑块审查 | 校准闭环核心 |
| `event_intelligence_service.py` 编排 | 🔴 高 | 审查每个阶段连接点 | 管道大脑 |
| 其他 `services/` 模块 | 🟡 中 | 重点关注错误处理 | 业务逻辑 |
| `models/` Pydantic 定义 | 🟡 中 | 检查字段约束和兼容性 | 数据契约 |
| API 路由 | 🟡 中 | 检查参数验证和响应格式 | 对外接口 |
| 前端组件 | 🟢 标准 | 参考前端标准 | UI 层 |
| 配置/环境 | 🟢 标准 | 检查新配置项文档 | 运维 |
| 文档 | 🟢 轻量 | 检查准确性 | — |

### 4.3 审查报告模板

每次审查应在 PR 中留下一个总结评论:

```markdown
## 审查总结

**审查者**: [姓名]
**审查时间**: [日期]
**总体评价**: [通过 / 需修改 / 不建议合并]

### 发现的问题

🔴 **P0 Blocker: X 个** — 必须修复
- [问题简述]

🟡 **P1 Suggestion: Y 个** — 应修复或创建 Issue
- [问题简述]

💭 **P2 Nit: Z 个** — 可选优化

### 值得肯定的地方
- [表扬好的代码/设计]

### 建议
- [如有架构层面的建议]
```

## 5. 特殊场景处理

### 5.1 紧急修复 (Hotfix)

| 方面 | 标准流程 | 紧急流程 |
|------|----------|----------|
| CI | 全部通过 | 最少通过测试 |
| 审查者 | 按分工要求 | 至少 1 人 |
| P0 阻断 | 必须修复 | 必须修复 |
| P1 建议 | 应修复/跟踪 | Issue 跟踪即可 |
| 合并条件 | 所有条件满足 | P0 修复 + 1 人批准 |
| 后续 | — | 24h 内完成完整审查回顾 |

### 5.2 大型重构 PR

- **原则**: 拆分提交，避免一次 PR 超过 500 行
- **策略**: 
  1. 先提设计文档 PR (仅文档，快速通过)
  2. 分阶段提代码 PR (每次 <500 行)
  3. 每个 PR 有独立的测试验证
- **如果必须大 PR**: 
  - 在 PR 描述中提供阅读顺序指南
  - 安排同步审查会议 (Pair Review)
  - 分文件/分模块分配给多个审查者

### 5.3 数据迁移 PR

数据迁移是最高风险变更，额外要求:

```
□ 迁移脚本在独立文件中 (如 backend/scripts/migrate_vX_to_vY.py)
□ 迁移脚本包含 dry-run 模式
□ 迁移脚本包含回滚方案
□ 在测试数据库上验证过迁移
□ 迁移后的数据完整性已验证
□ 对 JSON 文件包含备份指令
□ PR 审查必须包含架构审查者
```

### 5.4 依赖更新 (Dependabot / 手动)

| 更新类型 | 审查要求 |
|----------|----------|
| Patch 版本 | 确认 CI 通过即可合并 |
| Minor 版本 | 快速审查 changelog |
| Major 版本 | 完整审查，关注 API 变更和破坏性影响 |
| LLM SDK 更新 | 必须审查 + 验证 LLM 调用路径 |

## 6. 度量与改进

### 6.1 核心指标

| 指标 | 目标值 | 测量方式 |
|------|--------|----------|
| P0 逃逸率 | 0 (零 P0 问题进入 main) | 事后审查 + 线上问题统计 |
| 审查响应时间 | <1 个工作日 | GitHub PR 时间戳 |
| PR 存量 | <5 个待审查 PR | GitHub PR 列表 |
| PR 往返次数 | <3 轮解决 | PR 评论轮数 |
| P1 Issue 关闭率 | >80% (30天内) | GitHub Issue 统计 |

### 6.2 流程改进机制

- **月度审查回顾**: 每月回顾一次审查数据，识别反复出现的问题模式
- **标准更新**: 发现新的反模式或安全问题 → 更新 `CODE_REVIEW_STANDARDS.md`
- **审查者轮换**: 每季度轮换审查分工，避免知识孤岛
- **新人引导**: 新审查者前 3 次审查由资深审查者陪同 (Shadow Review)

## 附录 B: 快速决策树

```
收到一个 PR:
│
├─ CI 通过？
│   ├─ 否 → 等待 CI 修复，不进行人工审查
│   └─ 是 → 继续
│
├─ 变更涉及数据持久化？
│   ├─ 是 → 指派架构审查者
│   └─ 否 → 继续
│
├─ 变更 >500 行？
│   ├─ 是 → 建议拆分 / 安排 Pair Review
│   └─ 否 → 标准审查流程
│
├─ 发现 P0？
│   ├─ 是 → Request Changes，等待修复
│   └─ 否 → 继续
│
├─ 发现 P1？
│   ├─ 有 Issue → 可批准
│   └─ 无 Issue → 要求创建 Issue 后再批准
│
└─ 全部通过 → Approve ✅
```
