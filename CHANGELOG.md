# Changelog

### Fix: a calibration store that could not be read reported itself as idle

- **Two different states printed the same number.** Both reliability queries caught `Exception` and returned `{engine, competition, bins: [], total_samples: 0}`. A healthy store with nothing settled yet also reports `total_samples: 0`, so "the query failed" and "there is nothing to grade" were indistinguishable in the response, and a broken calibration dashboard rendered as an idle one. A check has three outcomes — `ok`, `empty`, `could not run` — and collapsing the last two into the middle one is how a failure stays invisible.
- **The error branch also returned a different shape.** It omitted `ece`, `max_calibration_error` and `sample_count`, plus `mean_confidence`, `mean_accuracy` and `signed_gap` on the confidence curve. Those are exactly the six fields the frontend's `ReliabilityData`/`ConfidenceReliabilityData` mark optional — the mismatch was being accommodated by the type, not fixed. Both branches now go through one `_reliability_unreadable` builder that emits the full success-path key set plus `error: "query_failed"`, a stable category rather than the exception text, following the convention already used at six sites in `api/routes/quality_metrics.py`.
- **The same DB problem produced two different HTTP results.** `get_kernel_session()` sat *outside* the try, so a store that failed to open raised through the route as a 500 while a store that failed mid-query answered 200-with-empty. Both are one operator problem; the open now happens inside the try, with a `session is not None` guard on the `finally` so the unbound case cannot raise `NameError` over the real failure.
- **No invented measurement.** The error path keeps `ece`/`max_calibration_error` at `None` and `total_samples`/`sample_count` at 0, and returns the **full empty bin list** rather than `[]` so a chart renders an empty axis instead of collapsing. The filter arguments are echoed back, since the dashboard labels the panel from them.
- **Dead code removed from both routes.** Each carried a normalization block whose comment claimed the success path returns `sample_count` but not `total_samples`; `_reliability_curve` has always returned both, so the `not in` guard could never fire. The routes now return the helper result verbatim.
- **Surfaced in the UI.** A 200 carrying `error` is not an SWR fetch error, so it previously fell through to the chart. Both panels gained a payload-level branch (`reliability-store-error`, `confidence-reliability-store-error`) that names the failure and says it is *not* "暂无样本", ordered after the fetch-error branch because the two are different failures. One unreadable curve still leaves the other rendered.
- Tests: 38 cases in a new `test_reliability_unreadable.py` plus 7 frontend cases. The key-set test is derived from the success path rather than hand-listed, so a field added to the curve cannot be forgotten on the error branch; the frontend suite includes the negative case that a genuinely-empty payload **still charts**, which is what separates keying off `error` from keying off `total_samples === 0`. 21 injections, all caught — the first pass found a real gap, where deleting the `finally` from the probability curve read GREEN because the close assertion covered only the confidence one.

### Fix: a factor that measured its inputs level was published as a home vote

- **Ten vote sites, two spellings, one bias.** Four binary engines resolved a factor's pick with `p >= 0.5` and six 3-way sites with `max(probs, key=probs.get)`. Both are position-dependent at a tie, and every engine's outcome dict lists `home_win` first, so a factor that ran, measured, and found the two sides **exactly level** was published as a home vote — and `factor_agreement` counted it. The explanation row shown in the UI named an outcome the factor never picked.
- **This is the common case, not a boundary curiosity.** All three binary engines compute `p_rest = 0.5 + rest_diff * 0.03`, so equal rest days give exactly 0.5 with the factor available. Measured over `kernel_match_fixtures`: **11,082 of 16,036 fixtures (69.1%)** carry at least one available factor sitting exactly on 0.5 — **88.5% of MLB, 56.9% of NBA, 46.2% of NHL**. The effect is systematically one-directional: an away-leaning prediction is always understated and a home-leaning one always overstated, because the invented vote is always `home_win`. Live examples: `mlb-824514` `bullpen P(home_win)=0.5` counted as home; `nba-21716138` `rest P(home_win)=0.5` counted as home **while the engine's own pick was away** (0.5052).
- **Fixed with two shared helpers, and the abstention is distinguishable from absence.** `factor_vote` returns `None` when the top two entries are equal; `binary_factor_vote` returns `None` at exactly 0.5. `factor_agreement` already dropped falsy votes, so an abstention now leaves **both** numerator and denominator — counting it as agreement would credit the pick with support no measurement produced. `available` stays `True`, so "measured and level" and "never ran" remain separable in the published row.
- **The triplication that made a drift invisible is gone.** Each binary engine wrote the same vote expression three times — once for `ContributionItem.predicted_outcome`, once for `compute_confidence`, once for `confidence_breakdown` — and the football engine did the same with three separate list comprehensions. All four now build **one** `votes` list and pass that list to every consumer, so the row the UI reads and the list `agreement` scores cannot diverge.
- **Reachability measured per engine, not assumed.** `EloOddsEngine` fuses on neutral ground, so equal Elo is an exact tie (`home_win == away_win == 0.3743`), and a symmetric book is another (`0.3596`); football's `elo` factor shares that lever. Dixon-Coles is the opposite: `elo_to_xg` bakes home advantage in (1.35 vs 1.15), so its tie basin is only **0.12 Elo wide** near `elo_diff ≈ -78.5` and **0 of 16,090** live fixtures land in it — pinned through the model boundary rather than a contrived fixture. Football's `_NEUTRAL_3WAY` is `{0.40, 0.30, 0.30}`, home-tilted by design, so the unavailable-factor fallback is deliberately *not* a tie.
- **Frontend mirror corrected too.** `sport-confidence-panel.tsx` reimplements `decision_strength` and its fallback is reachable in production — `_prediction_to_dict` does not send `betting_analysis`, so every match-detail page rendered from a *stored* prediction computes the panel locally. With the hardcoded `1/3` a binary coin flip displayed 33% where the backend scores 0%.
- Tests: 74 tests / 2 subtests across five new backend files plus a new `sport-confidence-panel.test.tsx` (9 cases). The key-order test constructs the *same* values in both orders and asserts `max()` returns a different key each time while `factor_vote` returns `None` both times, so it cannot pass because a dict happened to list `home_win` first. Every engine gets its level case **and its converse**, so no test passes by the factor merely being unavailable. The anti-drift spy patches the **engine module's** binding (the engines import the names directly, so patching `app.kernel.engines.confidence` would be a no-op) and asserts each confidence callee is invoked **exactly once** with a list equal to the published rows. `test_basketball_engine.py`'s `test_contribution_item_predicted_outcome_is_binary` was *corrected*, not loosened: its docstring asserted precisely what the defect made true, so it now first proves its own fixture contains no level factor.

### Fix: three of the five engines were scored against football's flat baseline

- **`decision_strength` hardcoded a 3-way baseline, and 3 of its 5 callers pass a binary distribution.** Its own summary line promised "flat -> ~0.0 useful signal", but the body computed `(peak - 1/3) / (2/3)`. For `basketball`/`baseball`/`hockey`, whose outcome space is `{home_win, away_win}`, flat means `peak == 0.5` — which scored **0.25**, not 0.0. The bottom quarter of the strength scale was unreachable for every binary sport, and since `compute_confidence` blends `0.50 * strength` into a `0.30 + 0.65 * raw` band, every stored binary `confidence` was inflated by `0.325 * (legacy - correct)`.
- **Measured on the live rows, then bounded over the whole corpus.** Recomputing the three stored binary predictions from their own probabilities reproduced their stored `confidence` exactly, which validates the model; under the fix they become `mlb-824514` 0.6788 -> 0.6037 (**-0.0751**), `nhl-2026010012` 0.5675 -> 0.4863 (**-0.0812**), `nba-21716138` 0.5854 -> 0.5050 (**-0.0804**). The inflation never gets small: because the factor clamps cap a binary fused peak at **0.7443 (nba) / 0.6525 (mlb) / 0.7223 (nhl)**, even the most decisive call an engine can physically make on a real fixture is still inflated by **0.0416-0.0710 (nba), 0.0565-0.0692 (mlb), 0.0451-0.0719 (nhl)** — present on all **16,090** live fixtures, not a tail.
- **It changed a published verdict.** `learning_service.confidence_calibrated` splits on a hard `0.5`, so the `nhl-2026010012` row crossed the threshold purely because of the baseline: 0.5675 was labelled a confident call, 0.4863 is not. `compute_confidence_reliability_bins` already documents that a positive `signed_gap` means overconfident and that "nothing else compares it to outcomes, so the confidence formula has had no empirical check" — this was the systematic component of that gap for three sports.
- **Football is untouched, bit-for-bit.** The baseline is now read off the arity (`1/n`) and the divisor is written `(n - 1) / n` rather than `1 - 1/n` **specifically** because `(3 - 1.0) / 3 == 2.0 / 3.0` is exact while `1.0 - 1.0 / 3.0` is not: at 1e-4 the two forms are indistinguishable, but end-to-end through the unrounded `compute_confidence` the `1 - 1/n` form moves **160 of 4,851** 3-way confidences by 1e-4. Verified over the whole **5,151**-point simplex grid at a 0.01 step: zero values differ. An `n < 2` guard returns 1.0 — a single-outcome distribution has no rival to be unsure about, and the divisor would be zero.
- Tests: 20 tests / 6 subtests in a new `tests/test_confidence_decision_arity.py`. The no-drift check keeps the pre-fix body as an explicit oracle and is itself guarded against vacuity by a companion asserting the *same comparison finds a difference at every binary point* — without it, making the two functions trivially equal would pass. The live peaks, the clamp-capped peaks and the 0.5-threshold flip are each pinned separately. 13/13 defect injections caught, including both partial reverts (baseline only, divisor only), the `1 - 1/n` float-drift form, and the `breakdown` path re-adding the quarter.

### Add: a prediction published two claims about who wins, and nothing compared them

- **Every stored prediction carries a scoreline *and* a set of probabilities, and for three engines they are computed from different evidence.** `elo_odds`/`dixon_coles`/football derive `predicted_scores` **from** the fused probabilities via `_probabilities_to_scores`, so the two agree by construction. `basketball`/`baseball`/`hockey` derive it from the raw Elo pair alone — `margin = (elo_home - elo_away + hfa) * coef` — while `outcome_probabilities` fuses every available factor. Elo carries **25.5% (mlb), 33.5% (nba), 35.0% (nhl)** of each engine's own weighted vote, so **65-75% of the evidence that moves the probabilities cannot move the scoreline**.
- **Measured on the live corpus: the two can name opposite winners on 71.5% of real fixtures.** Over the 16,090 fixtures in `kernel_match_fixtures` whose teams both resolve to a `kernel_elo_ratings` row (100% of nba/mlb/nhl), the published scoreline can name the opposite side from the fusion on **658/3,965 nba (16.6%) + 909 the other way (22.9%) = 39.5%**, **6,376/7,701 mlb (82.8%) + 1,277 (16.6%) = 99.4%**, and **1,557/4,424 nhl (35.2%) + 723 (16.3%) = 51.5%** — **11,500 of 16,090** in total. Confirmed behaviourally against all three real engines: holding Elo level at 1500/1500 and swinging only the non-Elo evidence to the away side yields `{home: 5.2, away: 3.3}` vs `away_win 0.552` (baseball), `{home: 110.9, away: 109.1}` vs `0.524` (basketball), `{home: 3.4, away: 2.1}` vs `0.5206` (hockey). Flipping that evidence back leaves `predicted_scores` **byte-identical** in all three.
- **The contradiction reaches the grading step.** `learning_service.compute_error` builds one `PredictionError` row whose `score_mae` comes from the Elo-only scoreline and whose `outcome_correct`/`brier_score` come from the fused probabilities. On a disagreeing fixture those metrics grade mutually contradictory claims about who wins, and `mae` is one of the optimizer's objectives. The scoreline is also rendered, fed to `soft_totals_from_scores` for the over/under recommendation, and averaged across engines by `ensemble_engine`.
- **Also measured and deliberately not "fixed":** the Elo-missing branch sets `margin = 0.0` exactly, so the scoreline is dead level no matter what the other factors voted — this is the live `nhl-2026010012` row (`2.8-2.8` beside `away_win 0.5003`, 3 of 8 factors available). It is **no longer reachable**: NHL Elo was seeded at 08:21:50 and that prediction ran at 07:35:27, 46 minutes earlier; Elo coverage is now 100% for all three sports. Separately, baseball still carries the pre-`f525669` form of hockey's margin line (`* 0.03` unclamped, where hockey was fixed to `_clamp(... * 0.015, -2.5, 2.5)`), but an expected score of <= 0 needs an Elo gap of 222 and the live maximum is 176, so `|margin|` never reaches `league_avg` on any real fixture (mlb max 7.129 < 8.5). Both are reported, not patched: changing a margin coefficient is a modelling decision, not a defect fix.
- **New read-only census + route.** `app/services/prediction_consistency_service.py` compares each stored prediction's two claims and reports `consistent` / `contradicts` / `score_even` / `unreadable` — four outcomes, because "could not evaluate" must never be counted as agreement. Exposed at `GET /api/quality-metrics/prediction-consistency`. The per-engine block is seeded from the declared `ELO_ONLY_SCORE_ENGINES` set, so an engine with no stored rows reports `no_predictions` instead of vanishing from the report and reading as healthy. A `draw` argmax beside a home-leaning scoreline is **not** flagged: the football path derives one from the other, so alarming on it would make the check broader than its meaning.
- Tests: 28 tests / 25 subtests. The behavioural pin holds Elo fixed and swings every non-Elo knob for each of the three engines, asserting the scoreline does not move *and* that the probabilities do — so a fixture that fails to exercise the fusion cannot pass silently. `ELO_ONLY_SCORE_ENGINES` is declared as data and pinned by that test: rewiring any one of the three to derive its scoreline from the fusion turns the matching subtest red. 23/23 defect injections caught, including all three engine rewires and the `_probabilities_to_scores` control.

### Add: five engines read three fitted artifacts, and nothing reported the state of any of them

- **The shipped Dixon-Coles fit did not converge, and the number it serves steers every draw probability in the system.** `backend/data/dixon_coles_params.json` carries `optimizer_success: false`. Its `rho = -0.0763` is read by `DixonColesEngine` and by `world_cup_rule_engine.calculate_outcome_probabilities` — which is itself called by the GBM engine, the AI engine and the legacy prediction engine, **five consumers**. Measured against `rho = 0` across plausible xG pairs, it moves the served draw probability by **+0.0134 to +0.0207**: 1.35/1.15 goes 0.2684 -> 0.2878, 1.0/1.0 goes 0.3085 -> 0.3292, 2.2/0.8 goes 0.1845 -> 0.1979, 1.6/1.1 goes 0.2489 -> 0.2670. A coefficient worth up to two points of draw probability came out of a failed optimizer and no log line, route, CLI or dashboard said so.
- **Ten keys the fitters already write had zero readers in `app/`.** `optimizer_success`, `since_year`, `min_team_matches`, `team_count`, `ref_date`, `fitted_at`, `feature_names`, `dataset_stats`, `validation_metrics`, `lightgbm_version`. This is the sixteenth instance of the same shape as `xg_source` and `matches_played`: a field is written, and the count of readers is zero. The fix is a reader, not another writer.
- `GET /api/quality-metrics/model-artifacts`, read-only and unauthenticated like the rest of that module. Per artifact: existence, fit age, `ref_date` age, sample count, convergence, staleness, the served coefficients, the training scope, the fit-quality numbers, and for GBM the feature-identity verdict. **Per-team attack/defense vectors are deliberately not returned** — a health report is not a model dump, and a test asserts no team name appears in the serialized response.
- **The roster is declared, so an artifact that was never fitted is named rather than absent.** Seeding the census from a directory listing would drop it, and a report over the survivors would read as fully healthy — the shape that let a league whose sync died pass as green two entries ago. `missing` / `unreadable` / `not_converged` / `unknown` / `ok`, with a `problems` list naming each unhealthy model so the operator does not have to diff a count against a total.
- **`unknown` is not `ok`.** The GBM trainer records no convergence flag at all, so the census reports `unknown` and quotes the held-out RMSE (home **1.392**, away **1.145**) instead. "We could not check" is not "we checked and it was clean", which is the same absence convention the optional discovery sources use. The first draft of the feature-identity call had exactly this bug in it: it returned `None` both for a clean artifact and for a check that could not import, so on an interpreter without `openai` the report printed `feature_identity: "ok"` on the same run whose log line said the check was unavailable. It now returns a distinct `unavailable`, and a test pins that the two are different values.
- **The BTD fit's own diagnostics record a draw-rate gap nobody read.** `empirical_draw_rate = 0.231784` against `boosted_draw_prob_neutral_off = 0.191611` — **-0.0402 absolute, -17.3% relative**, computed at fit time and read by nothing. It is now reported. It is *not* fixed: closing it needs a refit, which is a learning action.
- **The away booster shipped with no feature names.** `train_gbm_model.py` passed a hand-typed 17-name list to the home `lgb.Dataset` and nothing to the away one, so `gbm_away_model.txt` carries `Column_0..Column_16`; both feature-importance logs then read `train_data_h.feature_name`, labelling away gains with home names. Harmless only because the column order happened to match. **Four hand-typed copies of the 17 names** existed (two in the trainer, one in `backtest_gbm.py`'s ancestor, one written into the artifact as `feature_names` — the very list the serve-time check compares against); all now come from the shared `FEATURE_NAMES`. Note this does not retrain: the shipped away booster keeps its `Column_` names until someone re-runs the trainer.
- **The module whose stated purpose is preventing train/serve skew now checks feature identity, and the engine fails closed on it.** `derive_gbm_features` returns a bare positional list, so a booster fitted on a different column order does not raise — it returns a confident number computed from the wrong columns, and LightGBM only validates names when handed a DataFrame. `feature_identity_problem` compares the artifact's `feature_names` against `FEATURE_NAMES` (the only check that can see a **reordering**, which is the silent case) and each booster's `num_feature()` against the vector length. On disagreement `_load_models` returns `(None, None, meta)` and the engine serves `gbm_fallback_elo` with `model_loaded=False` — an honest answer, where a wrong-column xG is not.
- `backend/tests/test_model_artifact_health.py` — 48 tests / 17 subtests. The route path is asserted against `app.main`'s route table rather than a locally built `FastAPI()`, which would pass with the router never mounted. The trainer checks assert `feature_name` is not a list literal and that the trainer's `FEATURE_NAMES` **is** the serving module's object, because pinning a copy proves nobody reads the shared one. **20 defect injections, every one verified red**, restoration checked against `git diff --numstat`. Two of the tests were themselves rewritten because an injection found them vacuous: a booster-width assertion had the needle concatenated onto the haystack, and the coefficient-attribution fixture carried no `rho` for the defect to misattribute.
- Reported, not fixed: **the legacy BTD docstring states the wrong formula.** `world_cup_btd_model.py` documents the draw term as `sqrt(alpha_h * alpha_a)` while `app/kernel/engines/btd_model.py` documents `sqrt(alpha_h' * alpha_a)`. Both bodies compute `sqrt(alpha_h_effective * alpha_a)`, which is what `fit_btd_model.py`'s likelihood maximised, so the code agrees with the fit and the older docstring is the defect. Left alone here because changing it is a comment-only edit in a file this increment does not otherwise touch.

### Fix: the module that exists to prevent train/serve skew only ever fixed the column order

- **`derive_gbm_features` is shared by the training script and the engine precisely so the feature vector cannot drift.** It guaranteed the *order* of the 17 features and nothing else: both callers build `home_stats` / `away_stats` / `h2h` themselves and pass them in. Training built them over the last **10** matches and **10** meetings strictly before the fixture date. Serving called the producers with no arguments at all — which meant `get_historical_h2h`'s own default of **20** meetings (correct for its other consumers, wrong for this model) over *the most recent rows in the CSV* rather than the rows before the fixture.
- **The artifact already recorded the right answer and nothing read it.** `train_gbm_model.py` writes `training_config: {recent_window: 10, h2h_window: 10}` into `backend/data/gbm_features.json`, and `_load_models()` returns that metadata — the engine bound it to a local and never used it. This is the same shape as the `xg_source` field from two entries ago: written, never read. `resolve_windows(meta)` now reads it, and the artifact wins over the module constants, because the model was fitted with whatever it says.
- **Measured on the live prediction history before changing anything.** Of the **13** fixtures actually predicted by `prediction_method='gbm_lightgbm'`, **2** were served a feature vector the model was never trained on; `Portugal v Spain` had its away xG moved by **0.088** purely by the 20-vs-10 h2h window. Across the 18 plausible fixtures, **13** were off-distribution (largest shift **0.142**), and the features that moved were `h2h_avg_goal_diff` (12/18), `h2h_home_winrate` (10/18) and `h2h_draw_rate` (9/18).
- **The missing cutoff is leakage, and it is reachable rather than theoretical.** With no `before_date`, a finished fixture's own result is in the window used to predict it. **38 of 104** fixtures' served h2h includes a meeting on or after kickoff (all 38 include the fixture's own date) and **52 of 104** form windows include a post-kickoff match. It has not yet corrupted a stored prediction only because `international_results.csv` ends at **2026-06-25** and all 13 GBM predictions are later — an accident of the data cut, not a property of the code. Both call sites already held the kickoff: the kernel adapter has `MatchIdentity.kickoff_utc`, and in the *same function* of the legacy pipeline the hybrid/integrated branch passes `match.kickoff_utc` to `fetch_team_stats`/`fetch_h2h_data` while the GBM branch passed nothing.
- **Both call sites, not just the flagged one.** `GBM_ENGINE_ENABLED` defaults to false, but it gates the kernel adapter only — the legacy pipeline dispatches on the route's `engine` query parameter, which accepts `"gbm"` with no flag. So the reachable path was the unflagged one.
- **The windows are now declared once, in the module whose stated purpose is preventing this.** `train_gbm_model.py` and `backtest_gbm.py` import `RECENT_WINDOW`/`H2H_WINDOW` instead of each declaring `= 10`; three private copies of "10" is how serving came to use 20. A test walks both scripts' ASTs and fails if either assigns those names again.
- `backend/tests/test_gbm_train_serve_windows.py` — 17 tests / 28 subtests. The behavioural test asserts the served vector **equals** the trained-window vector feature by feature, with a companion test proving the 10- and 20-meeting windows actually disagree on that fixture, so a pass cannot come from the two windows being indistinguishable. **18 defect injections, every one verified red**, restoration checked against `git diff --numstat`.
- Reported, not fixed: **serving rounds and training does not.** `get_historical_team_stats` and `aggregate_h2h_meetings` round to 2 decimals; `_team_stats_before`/`_h2h_before` in the training script do not. At the 10-match window the rounding is identity, and on short-history pairs only 2 of 10 differ at all, by at most **0.0033** against a bound of 0.005. Removing it would change what the producers return to their other consumers, and aligning training instead needs a retrain — neither is worth 0.003 of a goal, so it is written down rather than acted on.

### Add: 584 fixtures kicked off and never got a result, and nothing reported it

- **A fixture with no `kernel_match_results` row cannot settle a prediction.** `fetch_outcome` joins that table, so no result row means no settlement, no calibration, no `direction_accuracy`, no engine score — silently, forever. The previous entry fixed the **writer** half for football (scores landed on the fixture row and never in the result table). This is the other half: the schedule sync stalls, the feed drops a game, or a fixture reaches `status="finished"` carrying no score at all, and the kickoff simply passes. Nothing anywhere reported that state.
- **Measured on the live kernel DB before the module existed** — **584** fixtures past kickoff with no result row:

  | competition | past-due, no result | oldest |
  |---|---|---|
  | mlb | 511 | 699d |
  | laliga | 25 | 30d |
  | ligue1 | 17 | 30d |
  | epl | 15 | 30d |
  | seriea | 15 | 30d |
  | nhl | 1 | 2d |

  **96 were more than 30 days overdue.** The oldest, `mlb-746577` at **699 days**, sits at `status="finished"` with **no score**, which is what makes it permanent: `backfill_results_from_fixtures` filters on scores being present, so it skips that row on every run and always will. **One real prediction (engine `baseball`) is already riding on a stale fixture**, so the cost is not hypothetical.
- **Two halves that need different operator actions, so they are counted separately.** `scored_but_unsettled` is the backfillable subset — run the backfill and it settles. The rest needs the feed. Collapsing them into one number would send the operator to the wrong command; the 699-day case is precisely the one a single total would hide inside "just run the backfill".
- **A competition that goes silent stays visible.** Every code in `BACKFILLABLE_COMPETITIONS` is named in the response even when it holds zero fixtures, and an empty one reports `no_data` — never `ok`. A league absent from the response is indistinguishable from a healthy one, and "we never had anything to check" is not "we checked and it was clean" (the same absence convention the optional discovery sources already use). Today that matters: bundesliga and ucl have **no 2026-27 fixtures at all**, which under an `ok` default would read as clean.
- **Age buckets, because "584 overdue" and "584 overdue by a day" are different situations.** `under_1d / 1_2d / 3_7d / 8_30d / over_30d`, last one open-ended, and `oldest_overdue_days` reported both overall and per competition.
- `GET /api/quality-metrics/fixture-freshness`, read-only and unauthenticated like the rest of that module, returning **aggregate counts only** — no match ids, no team names, no kickoff timestamps. A test asserts the serialized response contains neither a match id nor a `-home`/`-away` team name, so the footing is pinned rather than intended.
- **A real resource leak, found by the tests rather than reasoned about.** `kernel_db.get_kernel_session()` hands out a **new** `Session` per call and `close_kernel_db` only disposes the engine, so an unclosed session keeps a connection checked out — on Windows that surfaces as `PermissionError [WinError 32]` at temp-dir cleanup. The queries now sit in `try/finally: session.close()`, matching `kernel_db.get_latest_prediction`.
- `backend/tests/test_fixture_freshness.py` — 23 tests / 19 subtests. The route class mounts only the `quality_metrics` router on a bare `FastAPI()`: `app.main.app`'s lifespan re-initialises the kernel DB from settings, which would silently move the read off the temp DB the assertions are about. **14 defect injections, all verified red for the intended reason**, restoration checked byte-identically against `git diff --numstat`.
- **That bare-app mount is also blind to the failure this repo keeps rediscovering** — a working service with no way in. Every other test builds its own `FastAPI()`, so all of them would stay green if the router were never included in `app.main`. One test asserts the path off the production route table (not through a client, so the lifespan never runs), and commenting out the `include_router` line reddens **exactly** that one test while the other 22 pass.

### Fix: the h2h factor voted "impossible" off two matches, because the sample size was computed and thrown away

- **The count existed and never reached the engine.** `aggregate_h2h_meetings` returns `matches_played`; every producer runs through it; `enrich_situational_features` wrote `h2h_home_win_rate` and `h2h_draw_rate` and dropped the count. This became live only with the previous entry — before the result-row backfill, `h2h_meetings_from_kernel` returned 0 meetings for every club pairing.
- **h2h was the only one of the thirteen factors that fed a raw empirical rate straight into the blend.** Every sibling either goes through `_adjust_home_edge` — a bounded nudge away from neutral, floored — or bounds itself: the xG share cannot leave [0.25, 0.75] and the referee rate is clamped to [0.20, 0.80]. Driving all thirteen to their legal extremes on the real engine, the widest sibling vote was elo at `H=0.590`; h2h reached `H=1.000`.
- **Measured on the live kernel DB** (read-only copy, backfilled by the real `backfill_results_from_fixtures`): of **1446** upcoming football fixtures, **512** get an h2h vote and every one of them is built on exactly **n=2** — a league pairing meets twice a season, so the rate is quantised to {0, 0.5, 1}. All 512 votes were degenerate and **168 (32.8%) had an arm at exactly 1.0**:

  | rate home/draw | fixtures | vote before | vote after (n=2) |
  |---|---|---|---|
  | 0.0 / 0.0 | 71 | 0.000/0.000/**1.000** | 0.200/0.150/0.650 |
  | 0.0 / 0.5 | 108 | **0.000**/0.500/0.500 | 0.200/0.400/0.400 |
  | 0.0 / 1.0 | 26 | 0.000/**1.000**/0.000 | 0.200/0.650/0.150 |
  | 0.5 / 0.0 | 128 | 0.500/**0.000**/0.500 | 0.450/0.150/0.400 |
  | 0.5 / 0.5 | 108 | 0.500/0.500/**0.000** | 0.450/0.400/0.150 |
  | 1.0 / 0.0 | 71 | **1.000**/0.000/0.000 | 0.700/0.150/0.150 |

  On a real fixture (Elo 1900/1700, no odds) the factor moved `home_win` by **−0.118 to +0.082** at weight 0.05; after the fix, −0.078 to +0.022.
- **A ramp, not a clamp, because the sample size genuinely varies.** Over the historical international corpus (49,465 rows, 336 team keys, 7,535 pairings): 26.6% of pairings have one meeting, 43.6% two or fewer — but **23.8% have eight or more and 6.8% have 20+**. A 100%-home record votes 0.700 at n=2 and **0.924 at n=20**, so a real history still speaks.
- **This is deliberately a different shape from `_blend_h2h_venue`'s `clamp(n / _MIN_VENUE_SAMPLES)`.** That one mixes two *empirical* estimates and should reach the venue subset outright once it is thick enough; here there is one estimate and the question is how far to trust it at all, so it must never fully discard the prior. - **The floors are now one declaration.** `(0.01, 0.05, 0.01)` were inline literals inside `_adjust_home_edge`, which is exactly why the h2h vote had no floor — it was the one voter that did not route through that function. - **An unmeasured sample size is not evidence of a large one.** With the floors alone a 100%-home record still voted `H=0.943`, more extreme than any sibling can reach, so absent/zero/negative/unparseable `h2h_matches` falls to `_UNKNOWN_H2H_MATCHES = 1.0` rather than full trust. `n=0` is the trap worth naming: honouring it would give `w = 0` and vote *exactly neutral*, quietly turning "unknown" into "no opinion".
- **No existing test pinned any of this.** The engine suite's h2h fixture is `0.45 / 0.28`, an interior point that is never degenerate, and the four venue-split tests all assert *relative* order, which monotone shrinkage preserves. 484 football/adapter tests passed against the defect, and still pass — the venue mechanism is untouched.
- `backend/tests/test_football_h2h_sample_size.py` — 35 tests / 38 subtests. The census reads each factor's vote out of its own `ContributionItem.detail` (`H=x D=y A=z`), so it needs no mock and no spy: it parses what an operator sees. The production-door class writes no `h2h_matches` itself — it seeds two finished fixtures plus result rows and lets the real `h2h_meetings_from_kernel` → `aggregate_h2h_meetings` → `enrich_situational_features` chain produce the whole payload.

### Fix: the fan-out settings were validated on the route that cannot spend money and unvalidated on the scheduler that can

- **`/events/discover` has always declared `limit: int = Query(default=10, ge=1, le=50)`, behind `require_write_key`. The scheduler passes `settings.EVENT_DISCOVER_LIMIT` straight into the same function, and that setting had no bounds check at all** (`EVENT_DISCOVER_LIMIT: int = int(os.getenv(...))`). The operator-facing path was guarded; the unattended path that actually spends the money was not. `LLM_CONCURRENCY` had the identical shape.
- **Measured on the real collector before anything changed**, every source fetch replaced by a counting fake so no network or LLM call was made. Each source is asked for `limit * SOURCE_WEIGHTS[name]`, and the pool is capped at `limit * _CANDIDATE_POOL_FACTOR`:

  | `EVENT_DISCOVER_LIMIT` | largest single ask | total asks | pooled candidates → `analyze_event` calls |
  | --- | --- | --- | --- |
  | 1 | 3 | 5 | 3 |
  | 10 | 30 | 48 | 30 |
  | 100 (documented default) | 300 | 480 | 300 |
  | 1000 | 3000 | 4800 | 3000 |
  | 100000 | 300000 | 480000 | 300000 |

  Polymarket's weight of 3.0 means it alone is asked for three times the limit — at `limit=100000` that is a single adapter call requesting **300000** candidates. Nothing downstream bounds it: the 600s timeout bounds wall-clock but not the calls already issued, `LLM_DAILY_COST_CAP_USD` defaults to **0 (disabled)**, and the pool cap scales *with* the limit rather than bounding it. At the price table's `gpt-4` rate a `limit=1000` scan is ~$450.
- **The dangerous direction was down, not up.** A non-positive limit still fetched every enabled source and then sliced the pool to empty (`deduped[: 0 * 3]`), so a scan spent the outbound calls, analyzed nothing, persisted nothing, and reported **"未获取到任何候选事件 — 检查数据源…是否可达"** while every source was healthy and had answered. That is [`alarm-condition-broader-than-its-meaning`] again: a message naming a cause the branch never tested. `_src_limit`'s own `max(1, …)` floor is what kept a negative value from becoming an *over*-fetch, so the failure mode was a silent, source-fetching no-op on every scheduled run.
- **A negative limit also inverts the cap's meaning.** `deduped[:limit * 3]` with `limit=-1` is `[:-3]` — "everything except the last three", the opposite of an upper bound. It is unreachable through the fetch floor, but it is the pool cap's arithmetic, so a test pins the shape rather than trusting that the floor stays.
- **`LLM_CONCURRENCY=0` was the worst of the three.** `asyncio.Semaphore(0)` constructs without complaint and then admits nobody: every candidate blocks on `acquire()`, `asyncio.wait` returns `done=set()` after the full `EVENT_DISCOVER_TIMEOUT_SECONDS`, and the scan reports **"分析超时 (600s)，0 个结果保存"** — a ten-minute hang per scheduled run, attributed to a timeout instead of the config. `-1` raises `ValueError` *inside the scan* on the scheduler thread rather than at startup, where an operator would see it.
- **The fix bounds both at the settings boundary** with `_env_int_bounded`, in the same idiom as the file's existing `_env_bool` / `_env_csv`: `EVENT_DISCOVER_LIMIT` to **[1, 500]**, `LLM_CONCURRENCY` to **[1, 64]**, with the bounds exposed as `*_MIN` / `*_MAX` settings so tests and docs cite one definition. The floor is the same `ge=1` the route has always declared. The ceiling is a fat-finger guard an order of magnitude above the documented default, not a performance limit — at `limit=500` the pool is already 1500 candidates at ~8 outbound calls each, far more than the timeout can complete, so nothing legitimate lives above it.
- **Clamping with a warning, not raising.** A mistyped digit must not take the process down at import, and proceeding with a value that cannot work is worse than proceeding with the nearest one that can. The log line is part of the contract, so a test asserts the correction is *announced* (`EVENT_DISCOVER_LIMIT=0 … using 1`) and a second asserts an in-range value logs nothing.
- **`discover_events` holds the invariant at its own boundary too**, not only via the setting, so the no-op is unreachable from any caller rather than from the one path that was measured — the scoping mistake recorded in [`isolation-list-hand-maintained`].

Both directions are pinned: the warning fires when sources answered and the filters emptied the pool, and does **not** fire when the sources genuinely returned nothing.

### Fix: the rate limiter's "per client" bucket was either everybody's bucket or the caller's to pick

- **E3 「限流多实例 | 进程内计数；可信反代 IP 或 Redis」.** The backlog names two things and the measurement kept only one. "多实例" is not a live problem: `deploy/Dockerfile` and `backend/run.py` both start `uvicorn` with **no `--workers`**, and two subsystems already depend on that — `optimization_task_store.fail_interrupted_tasks` (`:223`) marks every task it finds `running` at startup as interrupted, which is only true if this process owned them all, and the scheduler is in-process. A per-process counter under a deliberately single-process deploy is sound, so adding a Redis dependency to share it would be speculative (CLAUDE.md §2). The other half was not just a gap — **both configurations of it were broken, in opposite directions.**
- **Measured before anything was changed, at `RATE_LIMIT_MAX_REQUESTS=2`.** With `TRUSTED_PROXY_HEADER=false` (**the default**) and a proxy in front, `request.client.host` is the proxy's address on every request, so **4 distinct real clients shared one bucket and clients 3 and 4 got 429** — `RATE_LIMIT_MAX_REQUESTS` is a *global* cap, and one busy caller locks everyone else out. With `TRUSTED_PROXY_HEADER=true` — which `deploy/docker-compose.yml` tells you to set — a single attacker rotating the `X-Forwarded-For` prefix got **8 of 8 requests allowed**: no limiting at all. So the flag's two positions were "throttle everyone together" and "throttle nobody".
- **The root cause is one index, and the comment defending it was factually wrong about this repo's own proxy.** `_client_host` read `chain[0]` — the **leftmost** entry — and both `config.py` and the existing forwarded-header test asserted in prose that the proxy "overwrites X-Forwarded-For". `deploy/nginx.conf.example` sets `$proxy_add_x_forwarded_for` (lines 99 and 123), which **appends**: the backend receives `<caller-supplied>, <real peer>`, leftmost is caller-controlled and rightmost is ours. The premise held for exactly one of the two shipped proxies, and the test that looked like coverage sent a **single-entry** header — true of Caddy, silent about nginx, which is why it stayed green through the bug.
- **Now read from the right, by a declared number of hops.** New `RATE_LIMIT_TRUSTED_PROXY_HOPS` (default **1**) says how many trailing entries our own infrastructure wrote, and the client is `chain[-hops]`. Default 1 is correct for **both** shipped proxies without further thought: nginx appends the real peer, Caddy's `header_up X-Forwarded-For {remote_host}` replaces the header with it. A CDN in front of nginx is 2. All `X-Forwarded-For` header instances are joined **before** slicing — a caller who splits the value across two same-named headers would otherwise push our entry out of the trusted tail.
- **The fallback never returns to the leftmost entry, because that is the shape a forger produces.** A chain shorter than the declared hops means the request did not come through the declared topology; falling back to `chain[0]` there would re-open the hole for anyone who simply sends one bogus entry. It falls back to `X-Real-IP` (both shipped proxies set it **overwrite-style**, so it is not caller-controlled), then to the socket peer. `hops` is clamped to a floor of 1 for a specific reason written at the clamp: `chain[-0]` **is** `chain[0]`, so a `0` in someone's `.env` would silently restore the original defect rather than fail.
- **The configuration a code fix cannot repair is now audible.** `TRUSTED_PROXY_HEADER=false` behind a proxy is a *deployment* state, so the app compares what it is told against what it sees and logs **one** `WARNING` per process: proxy headers present while the flag is off (the message contains `every caller shares one bucket`), or the flag on while no proxy header ever arrives (`not behind the trusted proxy`). Once per process, not per request — the setting only changes at restart, and logging every request is itself a denial of service. The latch is **instance** state on the middleware rather than a module global, so E10's singleton-reset census has nothing new to track.
- **Documentation was carrying the same wrong premise, so it moved with the code.** `nginx.conf.example` and `Caddyfile.example` now state which of append/replace they do and name both settings to put in `backend/.env`; `docker-compose.yml` says leaving them unset is not the cautious choice; `.env.example` and `config.py` describe the global-cap consequence instead of implying the default is safe; `docs/ops/RUNBOOK.md` gains the two measurement tables, a topology → hops table, the two warning strings to grep for, and the explicit note that the counter is still per-process. Two false claims that these examples' comments carried about an "audit log" were deleted rather than left as a promise nothing keeps.
- 10 backend tests added (`RateLimitTests` in `tests/test_operational_readiness.py`, 46 → 56 in that file): a rotating spoofed prefix cannot buy a fresh bucket, two real clients behind an **appending** proxy keep separate buckets, `hops=2` reads past the CDN hop, a short chain falls back to `X-Real-IP`, no `X-Real-IP` falls back to the socket peer, a header sent twice is joined before slicing, `hops=0` is clamped, and the three warning cases (headers-without-trust, trust-without-headers, matching configuration → silence).
- **One of the ten was vacuous, and only the mutation run found it.** `test_short_chain_falls_back_to_real_ip_never_the_leftmost` asserted that two requests **share** a bucket — which is true whether the key came from `X-Real-IP` or from the socket peer, because under `TestClient` both are constants. Deleting the `X-Real-IP` fallback therefore broke nothing. The test now also asserts that a **different** `X-Real-IP` gets its own bucket, which pins the key to the header: drop the fallback and both requests collapse onto the socket peer and the second one 429s. `assertions-that-cannot-fail` again — the same shape as E2's frontend badge test, one increment later.
- Verified by **11 byte-level mutations, every file restored byte-identically**: reading the leftmost entry again, reading the rightmost unconditionally, ignoring `hops`, dropping the clamp, dropping the multi-header join, dropping the `X-Real-IP` fallback, falling back to the leftmost on a short chain, warning on every request, warning in neither direction, and inverting the mismatch condition — each turns the suite red. After the fix the original exploit harness reports two `200`s then `429`.
- **Reported, deliberately not fixed** (CLAUDE.md §3), all written into the E3 backlog row: cross-process/cross-instance sharing (adding `--workers N` would multiply every limit by N with no warning — but it would break scheduler and task ownership first, so the rate limiter is not what guards it); `_prune` still walks every bucket per request (constant-factor waste, bounded by `_MAX_BUCKETS=4096`); `_enforce_bucket_cap` evicts by last-hit time, so a flood of distinct keys can evict a normal user's bucket and thereby **loosen** their limit; and the proxy's own `limit_req` and this middleware have no shared reading, so an operator cannot see which layer rejected a request.
- No engine, formula, weight or schema change; no route added or removed; no flag default changed — `RATE_LIMIT_ENABLED` and `TRUSTED_PROXY_HEADER` keep their existing defaults, and the one new setting defaults to the value that is already correct for both proxies this repo ships. No learning, scheduler, market write or prediction write enabled.

### Fix: the dashboard's busiest endpoint read the whole store twice for one answer, and archiving a batch rewrote a 3.5 MB file once per event

- **E1 「`event_store.json` 全量重写 | 规模债；归档/TTL 或迁 SQLite」.** Both paths the backlog names were measured before either was taken, and the measurement rejected the first one and sized the second out of a single increment — so what this increment removes is the **amplification**, not the format.
- **The cost of one pass, measured on the live store rather than assumed.** 3,622,538 bytes = **3.455 MB / 235 records** (median record 11,341 B). 20 iterations each: one `_load_unlocked` (read + `json.loads` + `normalize_event_record` per record) = **64.3 ms**; one `write_json_atomic` (serialize + `mkstemp` + `os.replace`) = **236.6 ms**. - **Archive/TTL cannot solve this, and the census is why.** Split by lifecycle: **130 records / 1.058 MB / 30.6% are resolved** — these are the calibration samples `list_resolved_events` feeds into the Brier aggregate, and evicting them would silently shrink the only measurement of whether the engine works; **94 / 1.062 MB / 30.7% are active**; **10 / 0.116 MB / 3.4% are archived-and-never-resolved**, which is the *only* category a TTL has the right to move out. A TTL would reclaim ~3% of the file and change none of the numbers above. (The fat is in a field, not in a lifecycle: `evidence_items` alone is **720.8 KB = 20.4%** across 186 records, then `legacy_analysis` 11.7%, `news_filter` 8.7%, `sentiment_profile` 6.2%. ### Fix: "reproducible seed=42" was not reproducible, and the gated metric's denominator was not the one the gate checked

- **Q1 「Model Eval Lab 常规化：固定评测集、版本号、发布门槛」.** Unlike Q3, this row was genuinely unimplemented — grep found no pinned eval set, no version field and no release gate anywhere in the repo. But the *reason* it mattered was a false claim already in the code: `scripts/model_eval_lab --sample N` advertised **"Randomly sample N resolved events (reproducible seed=42)"**, and `random.Random(42).sample` picks **positions**, so membership depends on the population's length and order. Measured on a 200-event population at size 50: growing by 1 replaced 2 members, by 5 replaced 7, by 20 replaced 10, and merely **reversing the list — which an `event_store.json` rewrite does (backlog E1) — left an overlap of 14 of 50**. Two runs a week apart were grading different events under one metric name. The routine eval was not comparable to itself.
- **Stable selection replaces positional sampling.** `select_event_ids` ranks candidates by `sha256(seed || event_id)` and takes the lowest N: order-independent entirely, and a growing population can only displace an incumbent one-for-one. The `\x00` separator is load-bearing — without it `seed="a", id="bc"` and `seed="ab", id="c"` hash identically, so two different sets could rank the same. Membership still moves as the store grows; that honest residual is what `--eval-set` is for, and the `--sample` help text no longer promises otherwise.
- **A fixed list of ids is not a fixed eval set.** A record can be re-graded *after* pinning (outcome rewritten, estimate replaced), and the same id then names different data while the score silently stops being comparable. Each pinned id carries a fingerprint over the eight fields the eval actually reads. A drifted event is **kept in the set and reported**, never dropped — dropping it would quietly shrink the denominator, which reads as "we evaluated the whole set" when we did not.
- **Fingerprints normalize every real number, not just floats.** A test caught the first cut: JSON `72` parses to an int and `72.0` to a float, so `repr(v + 0.0)` on the float branch alone meant a store rewrite that changed nothing but a value's *spelling* flagged the whole set as drifted — and drift detection that cries wolf is drift detection nobody reads. `repr(v + 0.0)` is also the shortest round-trip form, folds `-0.0` into `0.0`, and keeps `nan`/`inf` distinguishable instead of collapsing them into one "unusable" token. Bools stay untouched: `True` is an int in Python and must not fingerprint like `1.0`.
- **A digest mismatch is reported, never repaired.** Recomputing it on load would launder a hand-edited membership into an authoritative-looking artifact. `validate_manifest` returns *every* problem at once so an operator fixes one file once rather than one problem per run, and `--write-eval-set` refuses to overwrite without `--force` — a pinned set is the thing every past report was measured against.
- **The digest is a tamper seal, not a membership identity** — and it is named `digest`, which invites the other reading. Two `--write-eval-set` runs over the same live 130 events produced identical `event_ids` and identical fingerprints but digests `8e2a22bc...` and `e7d27b02...`, because `created_at` is inside the seal. So "different digest" does not mean "different set"; membership identity is `name` + `revision`, which is why a membership change is supposed to arrive with a revision bump. Documented on `manifest_digest` and pinned by a test, rather than left for an operator diffing two reports to rediscover — the `metric-name-lies` trap one layer up, in an artifact field instead of a metric.
- **The rule that separates a gate from an alert: a missing measurement must fail.** `quality_alert_service` documents "metrics with None values do not alert", which is right for paging — you do not wake someone because a slice has no data. It is wrong for certification: a report where Brier, ECE and direction accuracy are all `None` measured nothing, and letting it through would certify a model for having no evidence against it. The same `None` therefore means "no alert" in one consumer and "no pass" in the other; one test asserts both halves side by side, so making the gate "consistent" with the alerter turns it red. Each check records a `reason` so the distinction is visible in the output instead of implied by a threshold.
- **Second defect, found by running the new gate on the live 130-event store — the gated metric's denominator was not the one the gate checked.** `compute_ece` returned a float carrying no sample count. - **Report schema version and eval-set revision are different things**, and conflating them is how a stored artifact becomes unreadable. `REPORT_SCHEMA_VERSION` (1 → 2, the `eval_set` block) says which *layout* a report is in; `name`/`revision`/`digest` say which *events* were graded. The `eval_set` key is **absent, not None**, on an unpinned run, so a consumer cannot read "no pinned set" as "a pinned set that matched nothing".

### Fix: the per-domain trust weight was a direction hit rate wearing Brier's name

- **Q3 「来源域对 Brier 的贡献进权重」.** The row reads as unstarted wiring; it is not. The per-domain prior already reaches the weight: `source_reliability_service._shrunk_reliability(correct, sample, K)` → `prior_score` → `weighted_avg_tier_score` → **40%** of `overall_score` → downgrade rule #4 (`overall_score < score_threshold` turns a YES/NO into a WAIT). What flowed through it was `correct_count / sample_count`, where `correct` means only "the recommendation direction matched the outcome". A domain that keeps appearing on **51%-that-went-YES** events scored identically to one on **95%-that-went-YES** events — the `metric-name-lies` class again, and this one was already gating recommendations.
- **The Brier is taken from the FROZEN estimate, and there is deliberately no fallback.** `record["ai_probability"]` is rewritten by every re-scan, so a scan that ran after the outcome leaked would grade the model on an estimate it never committed to. The store reads `predictions.ai_probability`, which `freeze_prediction` writes once at first sight and never overwrites (`INSERT ... ON CONFLICT(event_id) DO NOTHING`) — the same row `score_prediction` grades. When the lookup yields nothing, `brier` stays `None`; a fallback to "the latest estimate" is exactly the defect P2-W2 fixed on the calibration side two increments ago.
- **Stance-adjusted, because one event-level Brier copied to every domain would credit the refuter with the supporter's score.** A supporting domain backed P(YES)=p, so its loss is `brier_score(p, actual)`; a refuting one argued the complement and is graded on `100-p`. At p=80 against a YES outcome that is 0.04 versus 0.64. Both are `None` together — a per-stance default would invent a loss for evidence nobody can grade. The flip degrades exactly to the existing binary rule (`correct = not rec_correct` ⟺ complement-Brier < 0.25).
- **What this attribution is NOT**, stated in the module docstring so nobody reads more into the number than it carries: a leave-one-out marginal contribution. Every domain on one event shares that event's probability, so neither measure discriminates *within* an event. Both discriminate *across* events, and only Brier does so with confidence weighting.
- **`brier_count` is stored apart from `sample_count`, and that separation is the point.** An attribution whose event was never frozen has no gradeable estimate. Folding it into `sample_count` would divide `brier_sum=0.5` by `sample_count=10` and report **0.05 — an EXCELLENT grade** — for a domain where exactly one event was ever gradeable. The API aggregate, the CLI table, the CLI summary line and the rebuild dry-run all print the graded share next to the total, so "0 graded of 400 samples" cannot masquerade as a flawless record.
- **Schema v1 → v2 through the store's own idempotent path.** `sqlite_db.apply_migrations` takes `column -> declaration`, skips columns already in `PRAGMA table_info`, and is safe to re-run; an existing v1 DB gets `brier_sum=0.0 / brier_count=0`, which reads honestly as "nothing gradeable yet" rather than as a perfect Brier. - **The metric swap is opt-in, because the two share a scale but not a distribution.** Hit rate and `1 - mean(brier)` are both [0,1] higher-is-better, but a coin-flip estimate scores **0.75** under Brier and **0.5** under hit rate — so switching raises every stats-backed prior across the board. `DOMAIN_RELIABILITY_PRIOR_METRIC` defaults to `hit_rate`, and with the default the emitted block is equal to omitting the argument entirely (pinned by a test). Anything other than `"brier"` reads as `hit_rate`.
- **Under `"brier"` a domain with no gradeable sample gets NO stats prior** and falls through to its tier default. Silently reverting to the hit rate would make the emitted `domain_stats_prior_metric` label a lie for that source — and provenance has to be recorded rather than inferred, since two metrics on the same 0-1 scale are indistinguishable after the fact.
- **NaN is rejected, not clamped, in both new numeric paths.** `min(100.0, nan)` returns `100.0` — every NaN comparison is False, so the clamp falls straight through and an unusable value would grade as a maximally confident call and, on a YES outcome, as a Brier of **0.0**. ### Fix: unmeasured venue depth was spent as a measurement of zero (P1-V3)

- Three defects in the sport-edge path, all one question: what does it mean that a venue publishes no liquidity? Every other liquidity site in this repo answers it the same way — `diagnosis_service.liquidity_factor` says "do not penalize what we cannot measure", `market_liquidity` omits the key rather than defaulting it, and `market_quality_service` excludes a missing sub-score from its average. The edge path answered it two other ways, neither of them that one.
- **`_aggregate_market_prob` treated unknown depth as a one-dollar market.** The weight was `max(liquidity, 1.0)` for a venue that publishes depth and `1.0` for one that does not — a sentinel spent on the same numeric scale as real dollars, making the unmeasured venue the *most distrusted* member of the group by a factor of thousands. Measured: a book quoting 0.50 with no published depth beside a $100 market quoting 0.20 produced a consensus of **0.2030**, of which the book held **0.99%**. Three such books all quoting 0.50 held **2.91%** between them. `raw_edge` inflated from 0.30 to **0.4470**, +49%, in the direction that manufactures edge.
- The weight for an unmeasured venue is now the **median of the published weights** — "assume this venue is typical of the venues that do publish", the minimum-assumption reading, and the only one that neither penalizes nor favours it. It preserves the real depth ordering among published venues, which an unweighted mean would discard: with an unmeasured book at 0.50, a $5k market at 0.20 and a $50k market at 0.60, the old rule gave 0.5636, an unweighted mean would give 0.4333, and the median imputation gives **0.5424** — three different numbers, so one test rules out both alternatives. Note that case corrects *downward*; the fix is not a one-directional thumb on the scale.
- **`_compute_liquidity_factor` contradicted itself.** Its own two documented rules are "an unmeasured venue is not penalized" (the all-unmeasured branch returned 1.0) and "the most liquid source dominates". Taking the max over only the *measured* subset honoured neither: it penalized a venue precisely because its depth could not be measured, and let the group's fate be decided by a member that is not the max once the unpenalized member is counted. One unmeasured venue alone gave 1.0; that same venue beside a $100 market gave **0.02** — learning that some *other* venue is thin cut the factor 50×, having learned nothing about the first. The factor is now 1.0 whenever any venue is unmeasured. This is a policy choice, the one the function already made for the all-unmeasured case, not a measurement: a venue that publishes no depth has an *unknowable* factor and arithmetic cannot supply one.
- **`fetch_link_price` sent traditional-odds links to the wrong venue**, which is why the mixed measured/unmeasured case is the *normal* case rather than an edge case. The Kalshi branch's own docstring diagnoses the failure — "sending it to gamma matches nothing and the link silently never gets a snapshot" — and the fallback then left it in place for the other source this class creates itself: `link_traditional_odds` stores a synthetic `odds_api::<match_id>::<outcome_label>` in `contract_id`, which gamma cannot match, so every poll spent an outbound request to learn nothing and the link never got a snapshot. It now returns None and names the reason. That does not create the gap — the gap already existed — it stops querying the wrong venue. Wiring `TraditionalOddsStore` into the snapshot path would be a market write and is deliberately not done.
- The two arithmetic fixes reduce **exactly** to the previous behavior when every venue publishes depth (nothing to impute, no unmeasured member) and when none does (no published weights to take a median of, so all weights stay 1.0 and the result is the unweighted mean it already was). Only the mixed case moves; two regression tests assert those endpoints and pass under both the old and the new rule, which is what makes them anchors rather than discriminators.
- The mixed case had **no test coverage at all**, which is how this survived. The one test whose name claimed to cover it — `test_detect_edges_traditional_odds_no_liquidity_uses_weight_1` — seeded a *single* link, and with one link the weight cancels out of the weighted mean entirely, so its assertions could not see the weight it named. Renamed, and six discriminating tests added; all six were confirmed to fail against the previous behavior before it was restored.
- Reported honestly: in the mixed case the two old defects pushed in opposite directions, so their product could look small by accident rather than by prudence (`adjusted_edge` 0.0089 where the corrected value is 0.3000). `PHASE7_EDGE_DETECTOR_ENABLED` remains **false**; correcting the arithmetic of an existing default-off path enables no learning, scheduling, market write, or prediction write.

### Confidence-reliability curve and signed calibration gap (P1-X1)

- The reliability curve that already existed bins `max(outcome_probabilities)`. `KernelPrediction.confidence` is a **different quantity** — built by `engines/confidence.compute_confidence` from decision strength, data completeness, factor agreement, and a market damper — and nothing had ever compared it to outcomes. So the engine's own stated confidence was rendered in the learning panel, consumed as a trust input, and never once checked against whether matches at that confidence actually resolved that often.
- `compute_confidence_reliability_bins` adds that curve, exposed as `GET /predictions/calibration/confidence-reliability` with the same bin shape as the probability route so the frontend chart is reused unchanged.
- Alongside ECE it publishes `signed_gap = mean_confidence − mean_accuracy`. ECE is unsigned and therefore cannot say which way to move the formula; the sign can. Positive is overconfident (rendered 过度自信), negative is conservative (保守). Both means are published so the gap can be read rather than trusted.
- The binning rule was extracted into one shared `_reliability_curve` used by both curves, so they cannot drift apart in bin edges, rounding, or ECE weighting. Two behaviors are preserved exactly: ECE accumulates from the **unrounded** bin means while `max_calibration_error` reads the **rounded** per-bin values the caller sees, and the bin index uses `min(int(predicted * bins), bins - 1)` rather than dividing by `bin_width` — `0.3 / 0.1` is `2.9999...` and put 0.3 in the wrong bin.
- Note the scale: `compute_confidence` maps its blend into `0.30..0.95`, so the lowest and highest bins are expected to be empty rather than missing. The panel says so, otherwise a correct chart reads as a bug.
- Every new fixture makes confidence and `max(outcome_probabilities)` different numbers (0.90 versus 0.55), so the two curves land in different bins and report different ECE (0.65 versus 0.30) on identical rows. Substituting the wrong column was confirmed to fail 8 of 17 backend assertions and 3 frontend ones before the correct binding was restored — the pre-existing reliability tests could not have caught it, since they asserted only bin counts and `total_samples`.
- Replaced a vacuous test in the process: `test_reliability_source_has_ece` asserted `"ece" in inspect.getsource(compute_reliability_bins)`. It pinned no value, and broke the moment the arithmetic moved into a shared helper with no behavior change.
- Read-only throughout. The endpoint writes nothing, no learning path is enabled, and no engine formula, weight, or output key changes.

### Real market over/under totals-line provider (P1-O1 真盘口)

- `market_totals_service`: opt-in configured over/under snapshots that replace the league-average placeholder line in the soft-totals diagnostic for football, NBA, NHL, and MLB — with bearer authentication, `http`/`https`-only endpoints, sport+date query resolution, bounded responses, strict validation, duplicate- and self-paired-fixture rejection, per-URL caching of valid snapshots only, and no-request behavior when disabled or unconfigured.
- The placeholder it replaces was not merely approximate; for the three North American sports it made the diagnostic vacuous. Those engines derive scores as `league_avg/2 ± margin/2`, so home + away equals `league_avg` exactly, and the soft-totals call is passed `line=league_avg`. Line and expected total were therefore identical by construction and **`p_over` was a per-sport constant** — measured at exactly `0.4821` for basketball at margins of 0, +5, +15, and −12 alike. Football escapes this only because `_probabilities_to_scores` applies a draw factor, so its expected total does move against its fixed 2.5 line.
- The provider must publish the line together with **both decimal prices**. A line on its own is a number with nothing behind it; a two-sided quote is what makes it a market. Prices are de-vigged locally, the overround must sit in `(1.00, 1.30]`, and the de-vigged over probability must be within `MARKET_TOTALS_MAX_PRICE_SKEW` of even — a book's posted total is by definition the level it has balanced, so a heavily skewed price means the number is not that level. The line must also fall in `[0.5×, 2.0×]` of the baseline it replaces, which catches a cross-sport unit error such as a basketball spread of 5.5 arriving as a total.
- Unpriced markets and malformed data are handled differently on purpose: a structurally broken row rejects the whole snapshot, while a row whose `over_odds` and `under_odds` are both explicitly `null` is a real fixture with a suspended or unopened market and empties only that fixture. `available=True, total=None` stays distinct from `available=False`; neither asserts the market is even.
- The request date is required as exactly `YYYY-MM-DD` and re-emitted canonically. Validating it loosely was a real defect found while testing: a whitespace-only date passed the original falsy check and was sent verbatim. A provider handed a timestamp or a partial date is free to ignore it and return another day's board, and a wrong-day snapshot looks perfectly valid while quoting lines for the wrong fixtures.
- Wired at **five** adapter call sites — `mlb_adapter`, `nhl_adapter`, `nba_adapter`, the football composition root `adapters/_shared.fetch_elo_and_odds` (EPL/UCL/league), and `world_cup_adapter._build_custom`, which builds `custom` itself and would otherwise have silently kept the 2.5 placeholder. Each site has a wiring test asserting the `(sport, kickoff-date, home, away)` call and that an unavailable or raising provider writes nothing, because a provider nobody calls is a capability that exists and is unreachable.
- Provenance is recorded as `soft_totals_btts["line_source"]` (`market_provider` / `league_average`), with the de-vigged book probability published verbatim as `market_p_over` alongside the model's own `p_over`. A malformed line in `custom` degrades silently to the baseline; a usable line with an unusable companion probability keeps the line. Engine formulas, weights, output keys, and default behavior are unchanged.
- The frontend panel badges the line source, shows a model-versus-book comparison tile when a book probability is present, and renders a caveat when the line and the expected total coincide — checked numerically (`|expected − line| < 0.05`) rather than by sport, so football's fixed 2.5 placeholder is not mislabelled.
- Caveat carried in the contract and in the panel: for basketball, baseball, and hockey the **expected total remains the league average**, so even with a real line the comparison measures the line's distance from that baseline rather than a team-specific scoring forecast. A team-specific expected total needs a scoring model those engines do not have.
- 亚盘 (Asian handicap) stays open on P1-O1: a spread line needs a margin distribution (Skellam or equivalent) that none of these engines expose, plus a frontend consumer that does not exist. Publishing a handicap with no margin model behind it would repeat the defect this provider was written to close.
- Production activation requires a licensed provider returning the documented contract; see `docs/dev/market-totals-provider-contract.md`.

### Fix: soft over/under was wrong at basketball scale (P1-O1)

- `soft_totals_btts_analysis` summed the match total over a fixed `0..10`-per-side score grid. At NBA scale (~110 points per side) essentially none of the probability mass falls inside that grid, so **`p_over` returned `0.0` and `p_under` returned `1.0` on every basketball match** — rendered directly to users by the soft-totals panel as `大 220 → 0.0% / 小 220 → 100.0%`. Hockey and baseball were also truncated, less visibly.
- The sum of two independent Poisson score counts is itself Poisson, so the over/under needs only a one-dimensional distribution over the total, not a two-dimensional score grid. The new `_poisson_total_pmf` builds that distribution in log space (`math.lgamma`) with a bound scaled to the mean (`lam + 10*sqrt(lam)`), so tail accuracy is constant across sports instead of degrading as the total grows. BTTS keeps its existing closed form.
- Measured effect: basketball at a 220 line goes from `0.0 / 1.0` to `0.4821 / 0.5179`; baseball moves `0.4674 → 0.4769`; hockey `0.4707 → 0.4711`; football is unchanged to four decimals, since the old grid was already wide enough there. All output keys, rounding, line semantics, engine formulas, and weights are untouched.
- Removed the `max_g` parameter from `soft_totals_from_scores`: it was declared with a default of `30` but never forwarded, so no caller could ever widen the grid.
- Regression coverage in `tests/test_soft_totals_distribution.py` pins the distribution properties — including a cross-check against an explicit two-dimensional convolution — and the previously vacuous `test_basketball_soft_totals` now asserts the probabilities instead of only the envelope. Both fail against the old implementation.
- Known limitation, unchanged and left to the real-market-line work: an exact total on an integer line still counts as under, which at a 220 line is ≈2.7% of the mass. Real push handling belongs with real market lines and an Asian-handicap feed, so `真盘口/亚盘` stays open on P1-O1.
